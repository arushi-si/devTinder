# Deploying Kodo

This checklist deploys the Kodo frontend to Vercel and the backend to Render, both on free URLs (no custom domain). The database stays on MongoDB Atlas.

```
browser ─► kodo.vercel.app            React app (Vercel)
        ─► kodo.vercel.app/api/*  ──rewrite──►  kodo-be.onrender.com/*    REST + login cookie
        ─► kodo-be.onrender.com       socket.io, direct, uses a 60-second token from /api/socket-token
```

**Why REST goes through `/api`:** if the browser called `onrender.com` directly, the login cookie would be third-party, and Safari would block it. Through the proxy, the cookie belongs to `vercel.app`, so it's first-party.

## 0. Before you start
- [ ] Push both repos to GitHub: `dev-tinder-be` and `dev-tinder-fe`.
- [ ] Make sure the Atlas cluster is running, and copy its connection string (**Connect → Drivers**). Add the database name before the `?`:
      `mongodb+srv://USER:PASS@cluster.xxxxx.mongodb.net/kodo?retryWrites=true&w=majority`
- [ ] In Atlas, go to **Security → Database & Network Access → IP Access List** and add `0.0.0.0/0`. Render's free plan has no fixed IP address, so this is needed. Use a strong database password.

## 1. Backend on Render
1. Go to render.com, sign in with GitHub, and choose **New → Blueprint**. Pick the backend repo; it reads `render.yaml`.
   - Or, without the Blueprint: **New → Web Service**, build command `npm ci`, start command `npm start`, health check path `/health`, then add the environment variables below by hand.
2. Set the region close to your Atlas cluster's region. It's `singapore` in `render.yaml`; change it if Atlas is somewhere else.
3. Environment variables:

   | Key | Value |
   |---|---|
   | `NODE_ENV` | `production` |
   | `NODE_VERSION` | `22` |
   | `TRUST_PROXY` | `2` |
   | `JWT_SECRET` | auto-generated by the Blueprint. Otherwise run `openssl rand -hex 32` |
   | `MONGODB_URI` | the Atlas string from step 0 |
   | `CLIENT_ORIGIN` | `https://<your-vercel-app>.vercel.app`. You don't know it yet, so put a placeholder and update it after step 2. |
4. Deploy. Then open `https://<service>.onrender.com/health`; you should see `{"ok":true,...}`.
   - The logs should show `db connected`.
   - If you see `ENOTFOUND` or a timeout, check the Atlas host and the IP access list.
5. Note the service URL. If the name `kodo-be` was taken, Render gives you something like `kodo-be-abcd.onrender.com`.

## 2. Frontend on Vercel
1. In the frontend repo, open `vercel.json` and make sure the `/api` rewrite points at **your** Render URL from step 1.5. Commit and push.
2. Go to vercel.com, choose **Add New → Project**, and import the frontend repo. Vercel detects Vite automatically: the build command is `npm run build` and the output is `dist`.
3. Environment variable: `VITE_SOCKET_URL` = `https://<service>.onrender.com`. Don't add a trailing slash. Don't set `VITE_API_URL`; production defaults to `/api`.
4. Deploy, and note the URL, e.g. `https://kodo.vercel.app`.
   - Vercel also creates preview URLs for each branch. Use the **production** domain.

## 3. Connect the two
- [ ] In Render, set `CLIENT_ORIGIN` to the exact Vercel URL (`https://kodo.vercel.app`, no trailing slash). Render redeploys automatically. This is needed for socket.io's CORS check.
- [ ] If you change env vars on Vercel later, **redeploy**. Vite reads `VITE_*` values at build time.

## 4. Check it works
1. Open `https://kodo.vercel.app/api/health`. The JSON `ip` field should be **your** IP address (compare with whatismyip.com). Rate limiting reads it from `x-vercel-forwarded-for` (see `src/utils/clientIp.js`).
   - If it shows a Vercel or Cloudflare IP, requests are not coming through the `/api` rewrite.
2. Sign up, refresh the page (you should stay logged in), then open `/feed` directly (it shouldn't 404).
3. In a second browser or a private window, sign up a second user. Swipe right on each other: you should get the match modal.
4. Chat between the two. Messages, the typing indicator and "Seen" should all update live.
   - In DevTools → Network → WS, you should see a connection to `onrender.com` with status 101.
5. Test on Safari or an iPhone. Login should work. This is the whole reason for the proxy.

## Troubleshooting
| Symptom | Likely cause |
|---|---|
| The first request takes 30–50 seconds | The Render free plan sleeps after 15 minutes with no traffic. Upgrade to Starter ($7/month) or accept it. |
| Login succeeds but the next request returns 401 | The frontend is calling `onrender.com` directly instead of `/api`, so the cookie is third-party. Check that `VITE_API_URL` isn't set on Vercel, and check `vercel.json`. |
| `/api/...` returns Vercel's 404 page | The rewrite destination in `vercel.json` is wrong, or the change wasn't pushed. |
| Chat says "Connection problem" or the console shows a CORS error | `CLIENT_ORIGIN` on Render doesn't exactly match the Vercel URL, or `VITE_SOCKET_URL` is wrong or missing (rebuild after fixing). |
| Socket fails with `Unauthorized` | `/api/socket-token` failed. Check that you're logged in, and that `JWT_SECRET` didn't change between deploys. |
| "Too many attempts" for everyone | The client IP isn't being read correctly; check that `/api/health` shows your own IP (check 1). |
| Everyone is logged out after a deploy | `JWT_SECRET` changed. Keep it stable. |

## Running locally (unchanged)
- Backend: `.env` from `.env.example`, then `npm run dev` (port 3000).
- Frontend: `npm run dev` (port 5173). No env vars are needed; it uses `http://localhost:3000` for both REST and socket.
